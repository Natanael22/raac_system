3. Entidades JPA
Crie uma classe base abstrata BaseEntity com os campos comuns. Todas as entidades herdam dela. Use Lombok para reduzir boilerplate.
3.1 BaseEntity (herança obrigatória)
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;
    @ManyToOne(fetch = FetchType.LAZY)
    
@JoinColumn(name = "tenant_id", nullable = false)
    private Tenant tenant;
    @CreatedDate
    private LocalDateTime createdAt;
    
@LastModifiedDate
    private LocalDateTime updatedAt;
    private LocalDateTime deletedAt;  // soft delete
}

4. Spring Security e JWT
Configure Spring Security 6 com autenticação stateless via JWT. Não use sessões HTTP. Cada request deve ser autenticado pelo token.
4.1 Filtros obrigatórios (ordem na filter chain)
CorsFilter: 
configurar origins permitidas por tenant
RateLimitFilter: 
100 req/min por IP usando Redis (INCR + EXPIRE)
TenantFilter: 
extrai tenant do header X-Tenant-ID ou subdomínio, injeta no TenantContext (ThreadLocal)
JwtAuthFilter: 
valida JWT, carrega UserDetails, seta SecurityContextHolder
4.2 SecurityConfig — rotas públicas vs protegidas
// Rotas públicas (sem autenticação)
.requestMatchers("/api/v1/auth/login").permitAll()
.requestMatchers("/api/v1/auth/forgot-password").permitAll()
.requestMatchers("/api/v1/auth/reset-password").permitAll()
.requestMatchers("/swagger-ui/**", "/v3/api-docs/**").permitAll()
.requestMatchers("/ws/**").permitAll()  // WebSocket handshake
// Todas as demais: autenticação obrigatória
.anyRequest().authenticated()
4.3 JWT — implementação obrigatória
Algoritmo: 
RS256 — par de chaves RSA 2048-bit. Gerar com keytool e armazenar no keystore.jks
Access token: 
expiração 30 minutos, claims: sub (userId), tenant, role, permissions
Refresh token: 
expiração 7 dias, armazenar hash no Redis com chave refresh:{userId}
Rotação: 
a cada uso do refresh token, invalidar o anterior e emitir novo par
4.4 Controle de permissões (RBAC)
Use @PreAuthorize nos métodos de serviço para controle granular por papel:
@PreAuthorize("hasAnyRole('ADMIN', 'ATENDENTE')")
public PatientResponse createPatient(PatientRequest req) { ... }
@PreAuthorize("hasRole('MEDICO')")
public MedicalRecordResponse createRecord(MedicalRecordRequest req) { ... }
@PreAuthorize("hasRole('FATURAMENTO')")
public BatchResponse createBatch(BatchRequest req) { ... }
5. Controllers e Endpoints
Todos os controllers seguem o padrão: recebem DTO de request validado com @Valid, chamam o service, retornam DTO de response com ResponseEntity. Nenhuma lógica de negócio nos controllers.
5.1 AuthController — /api/v1/auth
POST /login: 
LoginRequest(email, password, tenantId) → LoginResponse(accessToken, refreshToken, user)
POST /refresh: 
RefreshRequest(refreshToken) → LoginResponse
POST /logout: 
invalida refreshToken no Redis
POST /forgot-password: 
envia e-mail com token UUID, salva no Redis com TTL 2h
POST /reset-password: 
ResetPasswordRequest(token, newPassword) — valida token no Redis, atualiza senha
5.2 PatientController — /api/v1/patients
GET /: 
PageRequest + filtros (name, cpf, cardNumber, prontuarioNumber) → Page<PatientSummaryResponse>
POST /: 
@Valid PatientRequest (multipart para foto e carteirinha) → PatientResponse 201
GET /{id}: 
PatientDetailResponse com lista de convênios ativos
PUT /{id}: 
atualização parcial — apenas campos enviados
DELETE /{id}: 
soft delete (setDeletedAt)
GET /{id}/insurance-history: 
histórico completo de convênios
5.3 AppointmentController — /api/v1/appointments
GET /: 
filtros: doctorId, dateFrom, dateTo, status, type → Page<AppointmentResponse>
POST /: 
valida disponibilidade antes de persistir — retornar 409 se horário ocupado
PATCH /{id}/status: 
StatusUpdateRequest(status, reason) — registra em AuditLog
GET /waiting-room: 
lista pacientes com status EM_ESPERA ordenados por hora de chegada
5.4 AuthorizationController — /api/v1/authorizations
POST /: 
AuthorizationRequest → dispara @Async task, retorna AuthorizationResponse(id, status=PENDENTE) 202
GET /{id}/status: 
consulta status atual — frontend usa polling ou WebSocket
GET /: 
histórico com filtros por convênio, status e período
5.5 BillingController — /api/v1/billing
GET /guides: 
filtros: insuranceId, status, dateFrom, dateTo → Page<GuideResponse>
POST /guides: 
GuideRequest (a partir de appointmentId autorizado) → GuideResponse
POST /batches: 
BatchRequest(insuranceConfigId, month, year) → agrupa guias em lote
GET /batches/{id}/validate: 
valida XML TISS com JAXB contra XSD da ANS → ValidationResponse(valid, errors[])
POST /batches/{id}/submit: 
envia lote ao convênio via @Async
6. Integração TISS
Implemente o padrão de porta/adaptador (hexagonal) para isolar a lógica TISS de convênios específicos. A interface TISSPort define o contrato; cada convênio implementa seu adaptador.
6.1 Interface TISSPort
public interface TISSPort {
    AuthorizationResult requestAuthorization(TISSRequest request);
    EligibilityResult checkEligibility(String cardNumber, UUID insuranceConfigId);
    AuthorizationResult getAuthorizationStatus(String protocol, UUID insuranceConfigId);
}
6.2 Seleção do adaptador por convênio
Crie um TISSAdapterFactory que retorna o adaptador correto baseado no operatorName da InsuranceConfig:
@Component
public class TISSAdapterFactory {
    public TISSPort getAdapter(InsuranceConfig config) {
        return switch (config.getEnvironment()) {
            case DEV  -> mockAdapter;
            case HML, PROD -> switch (config.getOperatorName()) {
                case "BRADESCO"  -> bradescoAdapter;
                case "UNIMED"    -> unimedAdapter;
                case "SULAMERICA"-> sulamericaAdapter;
                default          -> genericTISSAdapter;
            };
        };
    }
}
6.3 Geração do XML TISS
Use JAXB para gerar e parsear o XML TISS. Os schemas XSD da ANS ficam em src/main/resources/tiss/xsd/. Configure o Marshaller para validar contra o XSD antes de qualquer envio.
// Validar XML antes de enviar
SchemaFactory sf = SchemaFactory.newInstance(XMLConstants.W3C_XML_SCHEMA_NS_URI);
Schema schema = sf.newSchema(new File("classpath:tiss/xsd/tissV3_05_00.xsd"));
marshaller.setSchema(schema);  // lança exception se inválido
MockTISSAdapter — cenários configuráveis (application.yml)
tiss.mock.scenario: ALWAYS_APPROVE  → autoriza imediatamente
tiss.mock.scenario: ALWAYS_DENY     → nega com motivo aleatório do catálogo TISS
tiss.mock.scenario: PENDING         → EM_ANÁLISE por mock.pending-seconds segundos
tiss.mock.scenario: TIMEOUT         → simula SocketTimeoutException
tiss.mock.scenario: EXPIRED_CARD    → beneficiário sem cobertura
tiss.mock.scenario: INVALID_CRED    → retorna HTTP 401 do convênio
7. Tasks Assíncronas
Use @EnableAsync na classe principal e @Async nos métodos de serviço que não devem bloquear o request. Configure um ThreadPoolTaskExecutor dedicado para tasks TISS.
7.1 Tasks obrigatórias
AuthorizationTask.sendAuthorization(UUID authRequestId): 
@Async — chama TISSPort, atualiza status, notifica WebSocket
AuthorizationTask.pollPendingAuthorizations(): 
@Scheduled(fixedDelay=300000) — verifica autorizações EM_ANÁLISE a cada 5min
NotificationTask.notifyAppointmentReminder(): 
@Scheduled(cron='0 0 8 * * *') — envia lembretes do dia seguinte
BillingTask.processBatchReturn(UUID batchId, String returnFilePath): 
@Async — importa XML de retorno, mapeia glosas
7.2 WebSocket — status em tempo real
Configure STOMP sobre SockJS. Após o resultado da autorização, publicar no tópico correspondente:
// No AuthorizationTask, após receber resposta do convênio:
messagingTemplate.convertAndSend(
    "/topic/authorization/" + authRequest.getId(),
    new AuthorizationStatusEvent(authRequest.getStatus(), authRequest.getAuthNumber())
);
8. Tratamento de Erros
Crie um @RestControllerAdvice global que capture todas as exceções e retorne um padrão consistente de erro:
// Formato padrão de resposta de erro
{
  "timestamp": "2024-01-15T10:30:00",
  "status": 422,
  "error": "VALIDATION_ERROR",
  
"message": "Dados inválidos",
  "details": [
    { "field": "cpf", "message": "CPF inválido" }
  ],
  "traceId": "abc123"
}
Exceção
HTTP Status e uso
EntityNotFoundException
404 — recurso não encontrado
BusinessException
422 — regra de negócio violada (ex: carteirinha vencida)
TenantNotFoundException
401 — tenant inválido ou inativo
TISSIntegrationException
502 — falha na comunicação com o convênio
DuplicateEntityException
409 — CPF ou e-mail já cadastrado no tenant
MethodArgumentNotValidException
400 — validação @Valid falhou (Bean Validation)
AccessDeniedException
403 — usuário sem permissão para o recurso
JwtException
401 — token inválido ou expirado

10. Testes
Use JUnit 5 + Spring Boot Test. 
Para testes de integração, use Testcontainers para subir PostgreSQL e Redis reais em container durante os testes — nunca banco em memória (H2) para evitar diferenças de comportamento.
10.1 Tipos de teste obrigatórios
Testes unitários (@ExtendWith(MockitoExtension.class)): 
para cada Service, mockando Repository e TISSPort
Testes de integração (@SpringBootTest + @Testcontainers): 
para Controllers com banco real — testar fluxos completos
Testes de segurança (@WithMockUser): 
garantir que endpoints protegidos retornam 401/403 sem autenticação
Testes TISS (@SpringBootTest com MockTISSAdapter): 
testar todos os cenários: aprovado, negado, pendente, timeout
10.2 Cobertura mínima
Services: 
mínimo 80% de cobertura de linhas
Controllers: 
100% dos endpoints com ao menos 1 teste de sucesso e 1 de erro
Segurança: 
testar cada role tentando acessar endpoint de outro role
